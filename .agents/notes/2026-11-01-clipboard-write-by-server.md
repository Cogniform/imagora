# 决策：「复制图片」改由本机服务端同步写剪贴板（2026-11-01）

状态：生效

## 问题

用户反馈：预览大图里点「复制图片」，界面立刻显示「已复制图片」，切到微信 Ctrl+V 什么都没出来；
多按几次偶尔成功；**停在页面上等 1 秒左右再粘就稳定**。

真机实测（有头 Chrome，127.0.0.1 安全上下文，复刻 `copyImageToClipboard` 全链路）：

| 观测点 | 结果 |
| --- | --- |
| `navigator.clipboard.write()` resolve | 2.6MB PNG 约 30~40ms |
| resolve 那一刻，外部进程读系统剪贴板 | `image=NONE`（还没有位图） |
| 多久之后才读得到 | 约 300ms 后 |
| 合成 4.2MB 图那轮 | `write()` 成功返回，剪贴板仍是**上一张**（整次静默丢弃） |
| 12MB JPEG 走 canvas 转码 | 转码 611ms，产出 17MB PNG（写剪贴板的数据量翻倍） |

结论：浏览器写图片是**异步投递**，Promise 的 resolve 只代表「请求已受理」，不代表「别的程序能粘」。
页面上那条成功提示比真实可粘早了一截，页面失活时更久甚至被挂起——所以「时间」不是关键变量，
**写有没有真的提交**才是。用户看到的两种现象（立刻粘是空的、停 1 秒就稳；切走再等两秒也不行）
都是这一条的表现。

## 决策

**复制的可信来源改成后端**：`POST /api/clipboard/image` → `core/clipboard.py` 用 Win32
`SetClipboardData(CF_DIB)` **同步**写，**接口返回即代表别的程序已经能粘到**（实测 275ms 往返，
返回后立刻读得到；16MB 大图 529ms）。前端只在写入真的完成后才显示「已复制」。

- 前端：`imageCopy.ts` 一条门面收口两条路 —— 有本机绝对路径 → 走接口；没有路径（外链 / blob /
  data URL）或接口不可用（非 Windows / 旧服务端 / 依赖缺失）→ 退回浏览器 `navigator.clipboard`，
  功能不因后端不可用而消失
- 反馈三态：`复制中…` → `已复制` / `失败`；进行中禁用两颗复制按钮（连点会并发写剪贴板，
  最后落地哪张不确定）
- CF_DIB 自己拼字节（`dib_bytes()` 纯函数）：40 字节 BITMAPINFOHEADER + 24 位 BGR +
  **自下而上** + 每行 4 字节对齐；这三条任一写错都是「不报错但图是坏的」，因此进单测
- **两种格式一起写**（2026-11-03 补）：`CF_DIB`（24 位、无 alpha）+ 注册格式 `PNG`（原字节、
  带 alpha）。首版只写 DIB，透明背景的 PNG 会被粘成黑块（透明像素 RGB 通常是 0，`convert("RGB")`
  等于把 alpha 扔掉）——而浏览器原路径本来两者都给，属功能退化。DIB 里的透明像素改为**合成到白底**。

## 替代方案（强制）

- **只改文案、不改实现**（resolve 后加固定延时再报成功）：治标，且延时取值没有依据；用户描述的
  「停 1 秒」在不同机型/图片大小上并不稳定。现在它只作为"后端不可用时的退路"存在（仍走浏览器路径）。
- **resolve 后用 `navigator.clipboard.read()` 回读校验**：需要 `clipboard-read` 权限，会弹权限框，
  为一个复制按钮弹权限不可接受。
- **前端把 PNG 字节发给后端、后端只做 CF_DIB 拼装**：省掉 Pillow 依赖，但 4096×6144 的图要过 100MB
  原始像素，内存与往返都不划算；Pillow 还能顺带吃 jpg/webp。
- **后端起 PowerShell + `System.Drawing` 转 DIB**：不引 Python 依赖，但每次复制都要付 ~500ms 进程冷启动，
  比 Pillow 的 100~300ms 慢，且把图片解码丢给另一套运行时，测试也不好写。
- **只写自定义 `PNG` 剪贴板格式（原始文件字节，零依赖）**：不用解码最省事，但微信 / Office / 画图读的
  是 CF_DIB，只给 PNG 格式它们拿不到图——这正是要修的场景，不能赌。
- **引导用户改用「复制路径」**：能绕开，但把修复成本转嫁给了用户；且路径对微信聊天场景不好用。

## 影响

- 收益：复制变成「返回即可粘」，不再依赖窗口焦点与异步渲染；"已复制"这个提示重新作数；
  CF_DIB 是 Windows 侧通用图片格式，微信 / Office / 画图都能直接吃。
- 代价：新增 `pillow` 运行时依赖（7 MB wheel，`uv.lock` 已更新，CI 用 `uv sync --locked`）；
  该能力仅 Windows，非 Windows 仍走浏览器路径（那条的时间差还在，属已知降级）。
- 边界：服务端进程退出后这份剪贴板数据会失效（应用在跑就没问题）；`OpenClipboard` 被别的程序
  （剪贴板管理器 / IM）占着时返回 0（err 5），`core/clipboard.py` 里做了短暂重试而不是直接报错。
- 记录层：本条取代早先「复制走 `navigator.clipboard`」的隐含假设；`docs/ARCHITECTURE.md` 7.1 与
  9.4 第 14 条是它的契约与防错条。
