# 决策：裁剪 / 放大走「派生新图」而不是原地替换（2026-10-20）

状态：生效

## 问题

画布图片节点原本只有「替换图片」一个改图入口（选中本地文件后原地换掉节点的 `registryId` / `url`）。裁剪与放大要接进来时，最省事的做法是复用同一条路：加工完把原节点 `data` 换掉。

但这两个操作和「替换」的语义并不一样。替换是「我拿错了，换成对的那张」；裁剪与放大是「我要基于这张图产出衍生版本」。用户对同一张原图往往要裁好几个比例（1:1 发朋友圈、16:9 发公众号、9:16 发小红书），原地换掉意味着每裁一次就把上一次的成果和原图一起丢掉，画布上再也回溯不到来源。

## 决策

裁剪 / 放大确认后走**派生新图**，链路固定为：

`对话框产出 data:image/png;base64,...` → `dataUrlFile.dataUrlToFile()` 转 `File`（`canvasUpload` 只收 `File`）→ 上传注册表 → `canvasEntriesToNodes` 在**源图右侧偏移 `DERIVED_NODE_OFFSET_X = 200`** 处新建图片节点（源节点已删则退化为视口中心 `getCreatePosition()`）→ `recordHistory()` → `pushLog`。

配套两条：

- **位置按源节点偏移而不是视口中心**：加工结果紧挨原图，用户一眼能看出派生关系；退到视口中心会让派生图和原图相隔可能半个画布。
- **`dataUrlToFile` 遇到非法输入必须抛错，不能返回空 `File`**：上传 0 字节会在画布上多出一个永远加载失败的红框节点，比当场报错难排查得多。

几何运算全部在前端 canvas 完成（`imageOps.ts` 的 B 层），**后端零参与**：不新增接口、不改 `generate_image` 契约、不引入新依赖。

## 替代方案（强制）

- **原地替换（复用「替换图片」链路）**：最省代码，但同一张原图裁第二个比例时前一个成果直接消失，且画布上无法回溯来源——与「派生加工」的心智模型冲突。这是本决策明确否掉的方案。
- **派生节点放在视口中心**：会与原图拉开随机距离，派生关系不可见；且连续裁三张会堆在同一位置互相遮挡。
- **派生图直接写进 `output/` 而不进注册表**：画布节点靠 `registryId` 定位文件、靠注册表做内容去重与引用计数（`refCount`），绕过注册表会让「引用 N 处」失效、删除节点时文件也不回收。
- **改后端加 `mask` / `crop` 参数走上游接口**：上游生图接口不支持裁剪，且这会新增一条必须维护的契约；纯前端 canvas 就能做完的事没有理由压给后端。
- **文件名用 `-1` / `-2` 序号**：序号要先查目录已有多少张，等于多一次网络往返；改用时间戳（`crop-红苹果-20261020-130405.png`），撞名由注册表按内容哈希去重兜底。

## 影响

- 画布图片节点的悬停操作栏从 3 个按钮变 5 个：预览大图 / 裁剪图片 / 放大图片 / 替换图片 / 删除图片。LOD 抽象模式下不渲染操作栏，因此放大到看不清时不会误点。
- 新增两个模块：`frontend/src/imageOps.ts`（几何纯函数 + canvas I/O，A 层有 49 个单测、B 层因 jsdom 无 2D context 不测）、`frontend/src/dataUrlFile.ts`（dataUrl → File + 派生文件名，11 个单测）。
- 新增两个对话框组件 `ImageCropDialog.tsx` / `ImageUpscaleDialog.tsx`，视口复用 `useImageEditorViewport`（移植自 basketikun/infinite-canvas，MIT）。
- E2E 从 46 断言增到 60：覆盖「入口按钮 → 对话框 → 确认后派生新节点且原图保留 → 裁剪产物还能继续放大」。
- 设计细节见 [docs/ARCHITECTURE.md](../../docs/ARCHITECTURE.md) 5.4 节「图片派生加工（裁剪 / 放大）」。
