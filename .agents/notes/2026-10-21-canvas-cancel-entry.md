# 画布取消入口：逻辑取消 + 本机意图压过旧快照

状态：生效

## 问题

issue #33：`POST /api/tasks/{id}/cancel` 与 `cancelTask()` 前端封装都在，`cancelAllTasks` 也早写好了，但**只有 `loadByName` 在加载工作流时会调**——用户界面上没有任何入口。一次「全部运行」排了十几张，想收回只能刷新页面（刷新也只是不看了，任务照跑照计费）。

## 决策

### 1. 入口：单卡「取消」+ 工具栏「取消全部 (n)」

- 单卡按钮出现在提示词卡底部操作行，**只在排队/生成中出现**，与「运行」按钮同一行。
- 工具栏「取消全部 (n)」**只在真有待跑任务时出现**（`activeTaskCount > 0`），数字就是待跑条数；它复用的正是原先无处可点的 `cancelAllTasks`。
- 「运行」按钮在排队/生成中本就禁用，所以「取消」在忙碌期是卡片上唯一可点的动作，不需要额外防误触。

### 2. 语义：逻辑取消，不是真中断

上游生图接口没有取消能力，服务端做的是：**排队中的取件前直接出队（永不发上游请求，不花钱）；运行中的跑完当前这张才作废**——产物仍落盘、仍计费，只是不派回画布。界面按这个口径写文案（README 中英文、ARCHITECTURE 5.3/8.2、frontend/README 节点条目），**不写「已停止」**：那会诱导用户以为没花钱。

### 3. 「取消中…」不立刻复位，且判定口径 = 本机意图 OR 服务端快照

- 点完先置节点 `cancelRequested` → 按钮变「取消中…」并禁用，**终态快照到达才清**（防重复点）。
- 只认服务端快照会出问题（复核发现的缺陷 D1）：秒数推送（每秒）与在途轮询拿到的都是**点取消之前**那份快照，它们把 `cancelRequested` 写成 false，卡片就退回可点，用户能重复点，与「取消期间禁用」的约定相反。
- 所以 `useGenerationTask` 里加了 `requestedCancelRef`：本窗口点过取消的任务，在终态之前始终盖上这层意图；**终态只认服务端那一份**（终态即意图结清，不留取消痕迹）。
- 兜底：服务端始终没认下（404/任务过期）时，轮询 catch 兜成 failed 并清掉意图，按钮不会永久禁用。

### 4. 取消后回 `idle`，不新增 `cancelled` 节点态

`CanvasPromptNodeData.status` 仍是 `idle|queued|running|done|failed`，取消落地后回 `idle`，只在**画布日志**留一行（服务端不记取消日志）。因为新增持久化的 `cancelled` 会动到节点 data 的语义（`core/AGENTS.md`：存储格式与字段语义属硬边界，须先经维护者确认），而界面并不需要区分「取消」与「没跑过」。崩溃恢复快照会剥掉 `cancelRequested`（`recovery.ts`），否则恢复出来的 idle 卡片会先闪一次「取消中…」。

## 替代方案

- **前端不显示取消，只提示「刷新页面」**：否决。任务照跑照花钱，用户诉求就是收回。
- **真中断上游请求**：否决。上游无取消接口；强行掐线程会留下半张图与对不上的账本行。
- **新增持久化 `cancelled` 状态**：否决（见上，触到 schema 硬边界），改用「回 idle + 日志」。
- **取消后立刻复位按钮**：否决。会撒谎（任务还在跑），且能重复点。
- **只在前端记「点过取消」不发请求**：否决。排队任务必须真的出队，否则 10 个 worker 立刻把它取走。

## 影响

- E2E `verify_canvas.py` 从 103 增到 **105 断言**：新增 1b 小节两条负向断言——「就绪卡片没有『取消』按钮」与「没有任务在跑时工具栏不出现『取消全部』」（E2E 不触发生成链路，忙碌态的出现/禁用/复位由前端单测钉住），并同步更新 5 处文档计数（AGENTS.md / ARCHITECTURE.md / frontend/README.md / tests/README.md / README_en.md）。
- 已知边界（复核记录，均不阻塞）：排队很长时按钮要等 worker 取件才复位；产物落盘计费不可逆；撤销可以把「运行中/取消中」还原成死卡（**既有问题**，本次未引入）。
