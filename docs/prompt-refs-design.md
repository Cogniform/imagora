# 提示词 `@` 引用参考图 · 设计

> 状态：**已实现**（解析层 + 提交接线；输入框内的自动补全弹层本版未做）

## 0. 一句话设计原则

**`@` 是在「已经连好的图」里做筛选，不是新开一条传图通道。**

| 原则 | 含义 |
|---|---|
| 连线声明集合，`@` 声明子集 | 画布连线决定「能引用什么」，提示词里的 `@` 只决定「这次用其中哪几张」 |
| 不写 `@` 就是旧行为 | 一个有效引用都没有时沿入边全收集，存量工作流一字不改 |
| 对不上就中止，不猜 | 写了名字却匹配不到，宁可报错也不静默换成别的图 |
| 标记止于前端 | 发给上游的提示词是 `stripPromptRefs` 之后的结果，模型永远看不到花括号 |

---

## 1. 为什么要把「沿边全收集」改成「只传被引用的」

### 1.1 旧口径的问题：连了几张就传几张

旧契约（[ARCHITECTURE 5.3](ARCHITECTURE.md)）只有一句话：提交时 `runNodeInternal` 用 `collectIncomingImages` 锁定入边参考图快照，图片组递归展开、`visited` 防环。这条口径本身没错——它把「这次用哪些图」完全交给画布连线——但它只有「全用」和「全不用」两档：

- 一个提示词节点上连了 10 张图、只想用其中 2 张 → 只能先删 8 条连线，跑完再连回来；
- 上游按图计费、按图占上下文：多传 8 张既多花钱，又把模型注意力摊薄到无关的图上；
- 想「这次用 A、下次用 B」就得反复改连线，而连线本应是稳定的编排结构，不该承担一次性开关的职责。

### 1.2 新口径：两段式，候选池 → 筛选

于是拆成两步（`collectPromptRefImages`）：

| 步骤 | 做什么 | 由谁决定 |
|---|---|---|
| ① 候选池 | `collectIncomingImages` 沿入边递归收集（图片组展开、`visited` 防环） | 画布连线 |
| ② 筛选 | `resolvePromptRefs` 按提示词里的 `@名字` 挑出子集 | 提示词文本 |

候选池**永远是**第 ① 步的结果，第 ② 步只能从中挑、不能扩，约束见第 3 节。

### 1.3 向后兼容：判定「有没有写过 `@`」而不是「筛出了几张」

回退的判据是**解析出的 token 数为 0**，不是「筛选结果为空」：

- 0 个 token → `mode === "all"` → 原样返回候选池（旧行为）；
- 至少 1 个 token 且全部匹配 → `mode === "explicit"` → 只返回被引用的（按出现顺序去重）。

为什么不按「筛出来几张」判断：`@` 一个都没写，和「写了但一张没对上」是两件事。前者是没启用新功能，后者是用户明确表达了意图却落空——后者必须报错（第 4 节），不能被当成「没写」吞掉。

## 2. 语法

### 2.1 三种写法

触发符是常量 `PROMPT_REF_TRIGGER = "@"`，解析层与插入层共用，避免两处各写一个字面量。

| 写法 | 例子 | 解析结果 |
|---|---|---|
| 简单形式 | `@cat.png` | 名字 `cat.png`，区间覆盖 `@` 到名字末尾 |
| 花括号形式 | `@{my cat.png}` | 名字 `my cat.png`，支持空格等简单形式吃不下的字符 |
| 转义 | `@@cat.png` | 字面量 `@cat.png`，**不产生引用** |

简单形式的字符集是 `[\w\u4e00-\u9fa5.-]`（字母数字下划线 / 中文 / 点 / 横线），**遇空格即停** —— 所以带空格的文件名必须用花括号形式。这也是 `promptRefInsertion` 存在的理由：按名字内容在两种形式间自动选，整串都是简单形式字符就写 `@name`，否则写 `@{name}`，让调用方不必自己判断。

花括号形式读到下一个 `}` 为止，名字内部不能含 `}`；`@{}`、`@{   }`（名字 trim 后为空）与**未闭合**的 `@{cat.png` 都不算引用——未闭合时整段按字面量放过，宁可漏认也不把普通文本误判成引用。

### 2.2 `@` 前面必须是边界

`@` 只有在**行首、空白或标点**之后才起引用；紧跟字母或数字的 `@` 是普通字符（判据是 `\p{L}` / `\p{N}`）。

理由很直接：提示词里写邮箱是常事，`user@example.com` 里的 `@example` 会被贪心吃成一个引用名，然后因为「对不上任何图片」把整次生成判成 `invalid` —— 一个和参考图毫无关系的邮箱就能让生成中止，属于把工具做成绊脚石。

## 3. 候选池 = 入边可达

### 3.1 唯一来源

`collectPromptRefImages` 的第一行就是 `collectIncomingImages(...)`，把结果映射成 `{id, name}` 候选再交给 `resolvePromptRefs`，没有第二条取图路径。

`collectIncomingImages` 的口径：从指向提示词节点的边出发向上游走，遇到图片节点收下，遇到图片组继续展开它的入边；`visited` 以提示词节点自身为种子，所以组连组成环时不死循环、同一张图经多条路径只算一次。

### 3.2 为什么不允许引用画布上任意图

如果 `@` 能引用画布上任何一张图，它就成了一条**绕过连线的传图通道**：连线本来表达「这次生成用哪些参考图」，看图就能看懂数据流；而一个只写在文本里的引用在画布上没有任何视觉痕迹，事后打开工作流根本不知道那张图从哪来。

所以 `@` 的定位是**筛选**，不是**引入**。这条也顺带保住了两条既有守卫：缺图守卫与「蒙版只能带一张」都作用在**筛选后**的集合上，于是 `@` 反而成了「只保留那一张带蒙版的图」的正经解法，而不是绕过守卫的漏洞。

### 3.3 与后端白名单同向

前端限制候选池，后端还有一道：[ARCHITECTURE 7.1](ARCHITECTURE.md) 里 `/api/generate` 的 `ref_paths` 只接受 `output/.refs/` 与 `output/.assets/` 两个目录内的路径（逐根 `commonpath` 校验，跨盘 root 单独捕获）。两道限制方向一致——参考图只能来自系统自己管过的文件，`@` 不提供任何例外。

## 4. 三种 mode

`resolvePromptRefs` 返回 `{mode, ids, unknown}`，`collectPromptRefImages` 再把它翻译成 `{images, unknown, mode}`：

| mode | 触发条件 | 传给上游的参考图 | 是否中止 |
|---|---|---|---|
| `all` | 提示词里一个有效引用都没有 | 候选池全部（沿入边全收集，旧行为） | 否 |
| `explicit` | 至少一个引用，且全部名字都匹配上 | 只有被引用的那几张，按出现顺序去重 | 否 |
| `invalid` | 至少一个引用，但有名字匹配不上 | 不提交（`ids` 里能对上的仍会返回，但当前调用方直接中止） | **是** |

### 4.1 为什么 `invalid` 必须中止

`invalid` 的典型成因：名字打错、那张图已被删除、或者图还挂在画布上但**没有连到这个提示词节点**。

这三种情况若静默处理，有两种坏法：

- 回退「全传」→ 用户以为只用了 `@cat.png`，实际传了 8 张；
- 降级「少传」→ 用户以为参考图生效了，实际一张没传，生成退化成文生图。

两种都是「图生成出来了、钱花了、结果不对，且事后无从察觉」。中止并报错的成本是一次点击，静默的代价是一整张废图加一次误判——所以 `CanvasPage` 在 `mode === "invalid"` 时清掉任务占位、写一条日志（列出对不上的名字 + 当前可引用的图片清单）然后直接返回，既不提交也不回退。

---

## 5. 发给上游前必须 strip

`stripPromptRefs` 把引用语法还原成纯文本：`@{my cat.png}` → `@my cat.png`，`@@` → `@`；简单形式 `@cat.png` 原样保留（本来就没有要剥的括号），孤立 `@`、邮箱、普通文本一律不动。

为什么必须剥：

- 模型不认识花括号写法，`@{cat.png}` 原样发过去就是提示词里的乱码；
- 花括号在部分模型里是**权重语法**，`@{...}` 可能被当成权重分组，把提示词语义整体污染。

实现上，`CanvasPage` 提交时传的是 `stripPromptRefs(data.prompt)`，而**画布上存的仍是原始提示词**——剥壳只发生在提交那一刻。编辑态的 `@` 语法必须留着，否则下次运行就没得解析了。

## 6. 名字匹配

### 6.1 精确匹配、区分大小写

两侧先 `trim` + 把内部连续空白折叠成单个空格，然后**逐字比对**，不做大小写归一。所以 `@Cat.png` 匹配不到 `cat.png`。

为什么不做模糊匹配（前缀 / 忽略大小写 / 编辑距离）：文件名相近的图太常见（`cat.png` 与 `cat-2.png`、`cat.png` 与 `Cat.png`），模糊匹配在「差一个字符」时必然要猜，而猜错的代价是整张图按错的参考图生成——比报错难发现得多。归一化也只做空白折叠，且刻意**不复用**下拉框那套 `normalizeCustomValue`：图片名的匹配规则不该跟着「自由输入框」的归一化策略一起漂移。

### 6.2 同名候选全部计入

画布上允许两个图片节点同名（不同目录的同名文件，或同一个文件拖两次）。`@same.png` 会按候选顺序把**全部**同名节点都收进 `ids`，而不是随便留一个：静默丢掉其中一个，等于替用户决定用哪张图。

### 6.3 最长匹配由 token 化天然保证

`@cat.png.bak` 解析出的名字是 `cat.png.bak`（点属于简单形式字符集），不会先命中 `cat.png` 再留下 `.bak`；反过来写 `@cat.png` 也不会被 `cat.png.bak` 抢走。这是「先切 token、再拿整串去比对」的直接结果，不需要另写一套最长匹配逻辑。

## 7. 输入框内的自动补全（本版未做）

`PromptNode` 的提示词输入框目前是**普通 textarea**（[CanvasNodes.tsx](../frontend/src/components/CanvasNodes.tsx) 里 `onChange` 只做 `onUpdate(id, { prompt })`），没有 `@` 触发的候选弹层，也没有引用高亮。

本版只做**提交时解析**：写对了就按引用传图，写错了在提交那一刻报错。`promptRefInsertion` 已备好「把名字插进提示词该写什么」的规则（简单形式 vs 花括号），但它目前只被单测覆盖、还没有 UI 调用点——补全弹层落地时直接用它拼插入文本，解析规则不用再动一次。

先不做弹层的理由：候选池依赖入边，输入时节点可能还在接线中；弹层还要处理光标位置、键盘上下选、Esc 关闭、与画布快捷键的冲突——这些成本换来的是「少打几个字」，而报错信息里已经把可引用的名字全列出来了。

## 8. 设计取舍

| # | 取舍 | 选择 | 理由 |
|---|---|---|---|
| 1 | 不写 `@` 时怎么办 | 保持旧的全收集 | 存量工作流提示词里没有 `@`，若改成「只用 0 张」，每个老工作流都会从图生图静默变成文生图 |
| 2 | 有名字对不上时 | 中止并报错，不回退 | 静默回退会让用户以为引用生效，钱花了、结果错了且无从察觉（4.1） |
| 3 | 候选池范围 | 只限入边可达 | 允许引用任意图 = 绕过连线传图，画布失去「这次用哪些图」的可视化声明（3.2） |
| 4 | 名字匹配 | 精确 + 区分大小写 | 文件名相近的图很多，模糊匹配会挑错图，挑错的代价是整张废图（6.1） |
| 5 | 发给上游的文本 | `stripPromptRefs` 之后 | 模型不认识花括号，且花括号在部分模型里是权重语法（5） |
| 6 | 输入框自动补全 | 本版不做 | 成本在光标 / 键盘 / 画布快捷键冲突，收益只是少打几个字；报错里已列出可引用名字（7） |

---

## 9. 明确不做的事

| 不做 | 为什么 |
|---|---|
| 引用画布外的图（任意路径） | 绕过连线，且后端 `ref_paths` 白名单也不接受（3.3） |
| 通配符 / 正则 / 目录级引用 | 一次引用多张收益低，且「到底传了哪几张」变得不可预知；真要全传，不写 `@` 就是全传 |
| 模糊匹配或大小写不敏感 | 见 6.1，挑错图的代价高于报错 |
| 静默跳过对不上的名字 | 见 4.1，用户会以为引用生效 |
| 输入框内的 `@` 高亮与补全弹层 | 见 7，本版只做提交时解析 |
| 把剥壳结果写回工作流 | 工作流存原始提示词，剥壳只发生在提交那一刻（5） |
